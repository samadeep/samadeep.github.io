# samadeep.github.io: working instructions

Samadeep Sengupta's engineering blog: https://samadeep.github.io. Astro 7, deployed to GitHub Pages from `main`.
These instructions are **self-evolving**: see "How this file evolves" at the end. Read it all before working here.

## Owner rules (never break)

- **No em dashes** anywhere: prose, code comments, commits, PR text. Use a comma, colon, parentheses or a new sentence.
- **Never name internal D.E. Shaw products, systems or details** in anything public. Describe work generically.
- **No Claude trailers, co-author lines or session links** in commits or PR descriptions.
- **Testimony needs his explicit yes.** First-person experiences, feelings, opinions and promises in his voice are written only from his own words. "Merge if you're happy" delegates the quality call, never testimony. First person is fine for things actually done for the post ("I ran", "I built the lab").
- **Evidence over "should work".** Build it, run it, screenshot it before calling it done. Say "I don't know" rather than guess an API, flag or number.
- **Merge only when he says "merge"** (or delegates and quality + testimony checks pass). Squash-merge through `gh api` REST (GraphQL is blocked from the agent workspace).
- Be token-economical; don't re-read or re-paste what's already known.

## How posts should read (current style)

Tags: **[his]** = he said it, so change it only when he does. **[ours]** = a convention Claude introduced; provisional, and the first thing to drop when a post feels formulaic or he pushes back.

- **Posts need life** [his, Oct 2026: "lack of life ... too verbose ... everywhere it's short answer XYZ then long answer"]. Open with a moment, a question or a surprise, never a dry summary: no "**Short answer:**" lead, no "the rest of this post covers..." roadmap. A **quirky TL;DR** above the opening is welcome [his, Oct 2026: "nice to have if written well, probably something quirky"]: `<aside class="tldr">` with `**TL;DR**` and one playful paragraph that ends on a twist ("The fix fits in one number per client. Yes, one."); if it reads like an answer box, cut it. There is no fixed skeleton: each post picks the shape its story has (a mystery for a bug, a journey for a build, a puzzle for CP, an explainer for an idea), so two posts never read alike. Talk to "you", ask questions, keep sentences short, let curiosity and a little humour show; cut every line that only restates.
- **Short** [his]. About 1,200 to 1,800 words of prose. Depth that would slow the main read (derivations, proofs, long tables) goes in fold-out `<details>` boxes ("The math", "Why this works"), so the post flows and the depth is one click away.
- **Life comes from him** [his]. Before drafting, ask for two or three lines in his own words (why it grabbed him, what confused him first, one opinion; voice notes and Hinglish are fine) and build the opening around them. Never invent them; without them, write warmly in the second person instead.
- **Explain deeper and simpler than the best existing explanation** [his, Oct 2026]. Self-contained: define every symbol, derive what matters with real math (`$$...$$`, typeset by KaTeX at build time) and check each equation with runnable code. Offer a collapsible "Before you start" box linking the best prerequisite reading (verified links) plus a notation table. Depth lives in fold-outs, so it never forces the main read past the length target.
- **Insights are rare** [ours, cut back after his Oct 2026 feedback]. At most one or two `> **Insight:** ...` callouts per post (rendered as a lightbulb), only where something truly lands: one or two sentences a reader could repeat to a colleague. An insight is a mechanism ("rules run once per connection"), a reframing ("serving is cache placement disguised as load balancing") or a transferable rule ("debug from the counter of the rule that should have matched"). It is never a summary of the section, a definition, or a claim about his feelings.
- **Readers run things, they don't read about labs** [his]. Every shell command goes in a ```bash block (it gets a ▶ Run button); small calculations go in ```python blocks. Don't narrate "the lab" or write "lab notes"; show the command and its real output. Evidence is called out briefly, limits go in a closing `<details>` block. **Sources are numbered references** [his, Oct 2026, from Lesley Zhou's post]: `[^key]` footnotes render as [1] in the text and a References list at the end (author, linked title, outlet, year); cite where the claim is made, not in a pile at the bottom.
- **A tiny visual simulator for the core mechanism** [his, Oct 2026, after PlanetScale's leaky-bucket post]. Each post's central mechanism gets a small animated widget the reader pokes: one or two knobs (−/+ or a slider), the thing moving, and live counters (admitted/blocked, hits/misses). Five seconds of play should make the idea physical. Build it like the stream and IceCube labs (`src/scripts/labs.ts` + its own module, inline SVG or canvas, colours from CSS variables so it follows the theme, works at 390px, honours reduced motion). Text-output Pyodide labs stay for exact numbers; the widget is for feel.
- **Borrowed from Cloudflare's best posts** [ours]: headings can be claims rather than labels ("API: the stream is a resource, not a connection", not "API"), but vary them; numbered claim headings on every post read like a template. Show the smallest complete thing first (the whole fix, the whole API), then "there's a lot underneath". End with a `## Try it` section that says how to run it on the reader's own machine. Commands meant for the reader's own machine (they'd fail in the browser VM, for example `npm install`) go in a ```zsh block, which gets no ▶ Run button.
- **Written to be picked up, then found** (from HN/X data, Oct 2026; the posts that spread state a surprising finding, generic "How to design X" titles never reach the top lists):
  - **Title says what the post is about** (the system or the task, e.g. "How to Design a ChatGPT-Style Streaming API"), at most ~60 characters. His call: a title built on one finding undersells a post that covers a whole design. The surprise goes in the first lines and on the share card instead. A catchy question title is fine when it names the subject (his pick for the Dust post: "Dust: Can We Really Do Away With Backpropagation?"); the description then carries the search phrase. Keep the URL slug if a title ever changes so shared links survive.
  - Description (at most 160 characters) carries the search phrases.
  - **The first lines carry the surprise** (the number, the moment), told as a story, not as an answer box.
  - **`hook: { stat, caption }` in front matter** puts the number huge on the share card (`src/pages/og/[slug].png.ts`); write `→` freely, the card draws it.
  - Pick topics with pull: a live debate, current AI-infra news, or a classic mechanism nobody has made runnable. Our edge is "runs in your browser"; say so on the card and in launch posts.
  - **Launch kit per post** (drafts only; he posts them himself): a 10 to 20 s screen recording of the bug for X (native video, link in the first reply), the share card, an HN title (the real post title, no editorializing; a blog post isn't Show HN, but a playable lab can be), and a LinkedIn text post.
- **Series are data, not code** (his call, Oct 2026: "make it dynamic"). Defined in `src/data/series.yml` (slug, name, `kind: weekly|collection`, icon, hue, blurb); a post joins with `series: <slug>` and everything else follows: the Series tab (`/series/`, one shelf per series, three newest posts each), `/series/<slug>/`, `/series/<slug>.xml`, the strip under the byline ("Issue 3 of 7" or "Part 2 of 4"), prev/next inside the series, the label on Writing rows and the share-card footer. Numbers are date order, never hand-written. A topic says what a post is about, a series says what kind of post it is, so every new post should pick one of each (add a series to the yml when a new format starts). Current shelves: CP Weekly, Algorithm Deep Dives, Papers Rebuilt, System Design, Build Logs. **CP Weekly is an essay about one mathematical idea, not a problem list** (his call). Arc: a short welcome (describes the series; anything in his first person needs his words), then the idea built from its smallest example, where it comes from (real papers and dates, verified), how it connects to neighbouring ideas, and only then the week's contest problem as the payoff, with figures and tested code, ending in "how to recognise it next time" (the method as a loop, plus the signals in a statement). Problem IDs stay out of headings; mention a problem only if it fits the idea. Models: cp-algorithms (history, motivating example before definitions), Jeremy Kun (concrete problem early, grounded in papers), Tao (ask the dumb questions, show the dead ends). Every claim is run in `public/labs/<slug>/`, solutions are checked against brute force, the lead is timed at max constraints; practice problems at the end.
- Topics: `algorithms`, `systems`, `low-latency`, `ai`, `science` (big results in physics and maths, made runnable; news-timed posts like a Nobel go here). Process detail lives in the `write-blog-post` skill.
- **System design posts** [his, reshaped Oct 2026] cover the interview arc (requirements with numbers, API, capacity in a runnable ```python block, the design diagram, life of a request, deep dives with evidence, failure modes, "what most diagrams get wrong"), but open on a real failure and phrase the deep dives as the questions they answer ("So who swallowed the 5 seconds?"), not "Deep dive N:". End by returning to the opening failure, not with a takeaways list; reference tables (data model) go in fold-outs. Be correct where typical diagrams aren't (for example, KV cache lives in GPU memory, not Redis).

## Diagrams: ```fig, laid out on a grid (the Agent Teams look)

- The bar is the Claude Code docs "Subagents vs Agent Teams" figure (his pick, and `fig` redraws it from ~30 lines). Its posture comes from layout, not colour: strict rows, one width per row, full-width bars, short straight arrows with small labels, titled grey panels. Text is the site's Aptos Mono (his call), not the reference's Nunito. Auto-layout (D2, Mermaid) can't do that, so posts use our renderer `src/lib/remark-fig.mjs`: ```fig title="<the conclusion>"``` -> one inline SVG, coloured by CSS variables in `src/styles/fig.css` (follows the theme toggle; no per-theme files). The first figure of a post is also written to `public/diagrams/fig-<hash>.svg` as its cover.
- **Grammar** (full notes at the top of `remark-fig.mjs`):
  - `panel <title>` starts a panel (side by side; `layout stack` stacks them, sharing one column grid, titles inside). `row` starts a row. `_` (or `_ 2`) is an empty cell.
  - Node: `id: <class> "Label\nsecond line" [span N] [icon <lucide-name>] [body "line\nline"]` (icon/body make a card). Classes: `main` (the thing in charge), `worker`, `peer` (clients, actors), `shared` (shared state, dotted), `result` (dotted circle), `allow`, `deny`, `ask`, `box`.
  - Edge: `a -> b "label" [lost|good|muted|dashed] [via left|right|below]`, `<->` for both ways, `r1 r2 r3 -> m "Report" muted via left` merges loop-backs onto one bus like the reference.
  - `seq` as the first line makes a sequence diagram: actors as nodes, then messages top to bottom (`f -> f "note"` is a note on f's lifeline).
- Place boxes so lines run straight: put a target in the same column as its source, use `_` cells to line things up, and reorder cells before reaching for `via`. Prefer side-by-side panels for "broken vs fixed" and "what you picture vs what happens"; wide, short layouts over tall ones.
- At most ~7 boxes per panel, labels of a few words, real values (IPs, ports, ms), never foo/bar. Caption states the conclusion.
- **Figures are numbered and described** [his, Oct 2026]: the renderer adds "Fig. N." and an `#fig-N` anchor, so prose can say "Fig. 1" and link it; every figure gets `alt="..."` describing the whole picture (what's in each box and what the arrows say) for screen readers and search.
- **Trade-offs get a spectrum figure** [his, Oct 2026]: when a post compares options, place them on one axis in a single row (panel title like `remembers more  →  remembers less`), with the odd one out on its own row, as in the rate limiter post's Fig. 2.
- Check every figure in light, dark and at 390px (narrow screens keep a readable minimum width and scroll sideways).
- Older posts use ```d2 (`remark-d2.mjs`) or ```plantuml; convert them to ```fig when you touch them.

## Running code in the reader's browser

- `src/scripts/vm.ts`: ▶ Run on ```bash/```python blocks types the command into a **real Linux VM** (Alpine, kernel 6.12, on the v86 emulator) in a docked terminal. A post sets `vm: { setup: '<command>' }` in front matter; it runs before the reader's first command.
- The VM image is built by `.github/workflows/vm.yml` (`vm/Dockerfile`, smoke-tested inside the VM, snapshot saved) and published to the `vm-dist` branch (`vm-dist-preview` off main); `deploy.yml` copies it to `/vm/`. Lab files from `public/labs/` are baked in; `curl https://samadeep.github.io/...` inside the VM is served offline.
- Emulation is slow (seconds to a minute per step). Anything heavy (thousands of connections) stays as recorded output with a note.
- `src/scripts/labs.ts`: `<div data-lab="py" data-src=... data-presets="a|b">` runs a Python file with Pyodide (instant, good for simulators; packages it imports, such as numpy, load automatically via `loadPackagesFromImports` in `public/labs/_runtime/py-worker.mjs`); `<div data-lab="stream">` is the streaming demo.

## Workflow

1. Branch from `origin/main`. `npm run build` and `npx astro check` (0 errors) before pushing.
2. Screenshot light, dark and 390px phone with Playwright (`executablePath: '/opt/pw-browsers/chromium'`) and look at them.
3. PR via `gh api repos/samadeep/samadeep.github.io/pulls`; list unverified claims and any first-person lines.
4. After merge, check the live page (the agent workspace can't reach the site; use the browser pane).
- Gotchas: fetch every external link before publishing, including old ones you keep: domains lapse and get hijacked (a 1024cores.net lock-free reference now serves gambling spam). Pyodide labs must load from `cdn.jsdelivr.net/pyodide/v<ver>/full/`; the npm package path has no package wheels, so `import numpy` fails only in a real browser (the workspace can't reach the CDN, so test labs live after deploy). A remark plugin error is only logged and `npm run build` still exits 0, so grep the build log for `error`. Killing by `ps | grep <name>` also matches the shell running that command (its own text contains the name) and kills it; record PIDs when starting background jobs and kill those. Old `.diagram svg` rules in global.css reach into inline SVGs; fig styles are scoped under `.fig-svg` to win. Never `pkill -f` (kills the agent shell); a process whose command line contains `node server.mjs` gets killed by the streaming lab's `stop_server`; Actions logs aren't downloadable from the workspace, so CI steps surface output as annotations (`vm/ci-run.sh`).

## How this file evolves

This file is the project's memory, and it must keep getting better with every interaction (his call, Oct 2026: "the entire thing should be a self-evolving thing"). It is never a static rulebook:

1. **Every interaction can change it.** When he corrects, redirects, states a preference or reacts to something (liked it or didn't), update the relevant section **in the same PR**, in his intent, tag it [his], and add one line to the log below. A new rule that contradicts an old one replaces it; never keep both.
2. **Rules have provenance.** [his] rules change only when he says. [ours] rules (conventions Claude introduced) are provisional: when output starts to feel formulaic, or he pushes back, revisit them first. Lesson: the "Short answer + an Insight per section" template was [ours], spread to every post and drained the life out of them before anyone questioned it.
3. **Bring him what's worth keeping.** When research or work turns up something good (a writing technique from a great blog, a better tool, a pattern that worked, a trap others hit), ask him in one line at the end of the task ("Found X; add it to CLAUDE.md?"), batched, never mid-flow. Add it only on his yes, tagged [his] once he approves.
4. **Gotchas go in immediately**, no need to ask: anything that cost time (a tool quirk, a CI trap) goes under Workflow so it never costs time again.
5. **Keep the skill in step.** When this file changes how posts are written, propose the matching update to the `write-blog-post` skill (it loses to this file in this repo, but other sessions rely on it).
6. **Prune as you go.** Keep it under ~150 lines: merge, rewrite and delete stale rules rather than append forever. Read the whole file before working here, and before finishing, ask: did anything in this session make a rule here wrong, missing or stale?
